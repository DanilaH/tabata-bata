# Архитектура

`TimerEngine` — чистый Kotlin, источник времени передаётся явно. Deadline текущего этапа сдвигается по расписанию этапов, а не от фактического времени вызова. UI и coroutine лишь запрашивают состояние. Поздний вызов перескакивает через истёкшие этапы без накопленного дрейфа.

`TimerService` владеет engine, sound cues и wake lock. Service стартует пользовательским действием, `START_NOT_STICKY`: нет неожиданного автоматического возобновления. StateFlow передаёт состояние Compose. Уведомление обновляется не чаще раза в секунду и при смене статуса; собственный канал без звука, чтобы не мешать сигналам таймера. Partial wake lock с ограничением длительности отпускается на паузе/завершении/destroy. FGS type `specialUse`, а не `shortService`/`dataSync`: таймер может быть длинным и работать без звуков.

Сессия checkpoint записывается в SharedPreferences раз в секунду и при смене состояния. После нового процесса восстановление только на паузе и вручную. Системные монотонные timestamp не переносятся между перезагрузками.

`Store` — DataStore Preferences для малого структурированного JSON списка и настроек. История хранится отдельно в SQLiteOpenHelper без новых зависимостей; связи между историей и изменяемыми режимами нет. Схема обмена v1; импорт проверяет параметры, размер файла до 1 MB, количество до 500, названия до 100 символов. ID импортированных режимов новые, импорт добавляет и не затирает существующее.

`Cues` — SoundPool, заранее загруженные короткие WAV. Используется USAGE_MEDIA с CONTENT_TYPE_SONIFICATION: сигналы зависят от медиагромкости, а не громкости системных кликов. Activity направляет кнопки громкости на STREAM_MUSIC. Новый сигнал отменяет старый; нет TTS/очереди голосовых команд. Ducking опциональный, используется кратковременный audio focus. Автопауза при потере фокуса применима только когда focus запрошен, она не является универсальным детектором звонков. Нельзя обещать распознавание любого звонка без отдельной проверки.

Нельзя считать foreground service абсолютной защитой от OEM ограничения батареи, force stop или системного убийства. WorkManager/AlarmManager не используются как движок двухсекундных интервалов.


`HistoryRepository` хранит неизменяемый снимок плана/названия/оформления, статус и статистику TimerEngine. Перед остановкой service один terminal commit в session SharedPreferences атомарно заменяет active checkpoint на pending history record. IO-worker переносит очередь в SQLite с sessionId PRIMARY KEY / INSERT OR IGNORE, затем подтверждает очередь; смерть между DB commit и подтверждением не дублирует запись. Смена Activity, показ результата и повтор не записывают историю. Каждая новая сессия имеет новый ID; восстановление сохраняет ID.

Календарные даты используют wall-clock только для подписи и границ локальной недели (понедельник, с учётом DST); активное время остаётся монотонным из engine. SQLite индексирует finished_at; UI читает по 50 записей, недельный SUM/COUNT выполняется по всему диапазону. Неполная статистика старого checkpoint явно отмечена и исключена из суммы времени. Пользовательский текст/планы не передаются в новые события аналитики. История не включена в прежний экспорт JSON v1 и не восстанавливает старые занятия из AppMetrica.
