# Закрытие замечаний к 0.11.2: SDK и системная навигация

Задача: локализовать и закрыть два открытых пункта предыдущего визуального аудита. Версия исправления: 0.11.3 / code 24, продуктовый код `9f18a803d80b4c8d29bed158496ddebbc02f97da`. Исходная версия для сравнения — 0.11.2 / code 23 (`652e02a9abb37d94a9c1dbccab0ba686b5e3c56a`).

## Межстраничная реклама

Код `Ads.kt`, политика показа, постоянное удержание ссылки на fullscreen и обработчики SDK не менялись. Исправления относятся к тестовому размещению, управлению и окружению реального demo SDK:

- Изолированный баннер обёрнут в safeDrawing-контейнер: раньше эта самостоятельная тестовая сцена размещала его частично под статусной строкой. Основное приложение уже использовало свои safe areas.
- Для видео настроены PulseAudio/null sink, явные `QEMU_AUDIO_DRV=pa` и `PULSE_SERVER`, убран `-noaudio`, сохранены обычные анимации. В гостевом Android задан DNS. В неудачных логах были продолжительные `ranchu pcm_writei failed` и DNS/ECONNREFUSED; одним успешным прогоном их устранение не объявляется доказанным.
- Устранено запоздалое нажатие «Назад» в тесте. Между проверкой условия цикла и отправкой ввода находилась секундная пауза. За это время SDK мог уже закрыть AdActivity. Тест продолжал распознавание SDK-контролов на главной, содержащей video-баннер, и мог нажать Back в меню, завершив MainActivity.
- Dismiss теперь прекращается после реального `ad_closed` или возврата MainActivity в RESUMED. Условие повторно проверяется после паузы. Перед проверкой меню ожидаются RESUMED и фокус окна приложения.

Доказательство гонки: в [прогоне 43202503057](https://github.com/DanilaH/tabata-bata/actions/runs/43202503057) Yandex получил два настоящих `ad_closed`; прямой показ и баннерные safe areas PASS. Единственное падение — `No compose hierarchies` на проверке главной: MainActivity уже возобновилась в 10:46:47.302 UTC, `ad_closed` пришёл в 10:46:47.372, после чего лишний ввод завершил Activity. Это тестовая гонка после исправного закрытия, а не отсутствие SDK callback.

Первый [прогон 43196610350](https://github.com/DanilaH/tabata-bata/actions/runs/43196610350) был полностью зелёным, но повтор на 0.11.3 снова выявил проблемы — его одного недостаточно для вывода о стабильности. Финальная проверка с исправленным владельцем ввода, safe areas и окружением — [43203951249](https://github.com/DanilaH/tabata-bata/actions/runs/43203951249): configured build/lint, Yandex и HTML — все три jobs PASS. В каждом demo-профиле по 3 теста, 0 failures/errors/skipped; по одному настоящему ad_closed в прямом показе и в результате настоящей тренировки. Всего подтверждены четыре закрытия SDK. Аудиоошибки эмулятора полностью не исчезли, поэтому они не объявляются единственной доказанной причиной всех прежних падений.

Обязательны реальный `ad_closed`, возврат в меню, суточный лимит, отсутствие prefetch после успешного показа, ограничения первого занятия/Stop и minified offline smoke. Таймауты и demo IDs не ослаблены. Production-реклама в этих тестах не запускается.

## Системная панель

Проверяется отдельно на Android 15/16: обычные системные касания, показ и скрытие настоящей IME, переход к занятию и пауза. Длинный сценарий сначала проходит 13 UI-сценариев, затем завершает инструментальный процесс и повторяет нативное управление. При локализации сохранены WindowManager, IME, SystemUI и Quickstep/taskbar dumps. После локализации постоянный сбор полных дампов убран: он мешал наблюдению на загруженных AVD. Обычная регрессия сохраняет снимки и необходимые window insets; временные ошибки только read-only команд ограниченно повторяются.

В новой нативной проверке исправлено ошибочное ожидание: выход из нового редактора автоматически сохраняет черновик и возвращает домой; подтверждение сброса бывает только там, где оно действительно требуется. Это исправление сценария, не изменение продукта. Видимая IME проверяется по системному состоянию, а не предполагается после нажатия.

Нативный AOSP-прогон [43197835391](https://github.com/DanilaH/tabata-bata/actions/runs/43197835391) повторил серые кнопки уже после короткого реального IME-сценария. Получена локализация по независимым данным:

- WindowManager применяет appearance `0` для тёмного занятия; IME уже скрыта.
- SystemUI: `mNavigationLight=false`, `mHasLightNavigationBar=false`, `mNavbarColorManagedByIme=false`, `mDarkIntensity=0.0`, `mNextDarkIntensity=0.0` — запрос и расчёт белых кнопок правильные.
- Quickstep: `mTaskbarNavButtonDarkIntensity=0.0`, но `mOnTaskbarBackgroundNavButtonColorOverride=1.0`, `mOnBackgroundNavButtonColorOverrideMultiplier=1.0` — цвет насильно заменяется собственным цветом панели.
- На пикселях Home имеет RGB `[69,70,79]` поверх `[78,57,18]`; это подтверждает видимый серый цвет независимо от запрошенных appearance-флагов.

В [Android 15 NavbarButtonsViewController](https://android.googlesource.com/platform/packages/apps/Launcher3/+/refs/heads/android15-release/quickstep/src/com/android/launcher3/taskbar/NavbarButtonsViewController.java) ветка updateNavButtonColor безусловно применяет этот override. В [другой опубликованной ревизии Launcher3](https://android.googlesource.com/platform/packages/apps/Launcher3/+/3e63886c6e1996875e702a62ebbf1f54925df6fc/quickstep/src/com/android/launcher3/taskbar/NavbarButtonsViewController.java) для phone mode уже есть ветка, сохраняющая цвет SystemUI. Это локализует наблюдаемое нарушение в системной панели проверяемого AOSP-образа. Перезаписывать системные настройки телефона из приложения ради теста нельзя.

Воспроизведение на Google APIs также показало тот же серый цвет. Замена образа сама по себе не считается исправлением. Все визуальные workflow используют Google APIs; AOSP дополнительно остаётся в общих проверках совместимости. Добавлена автоматическая проверка именно физического контраста кнопки Home и фона >=3:1 после настоящей клавиатуры в контролируемом портретном 3-button phone профиле. Используется raw RGBA Android screencap, без дорисовки и без доверия одному appearance-флагу. Планшет имеет другую геометрию taskbar и проверяется визуально отдельно. 
### Защита в приложении

В `MainActivity` добавлена отдельная поверхность для трёх системных кнопок. Фон и запрашиваемый цвет значков соответствуют системной светлой/тёмной теме телефона, а не текущему цвету этапа или сохранённой Compose-теме приложения. Поэтому и штатный tint SystemUI, и переопределение Quickstep остаются читаемыми. Фон создаётся штатным navigationBarColor (он продолжает действовать для 3-button navigation на API 35+) и системным контрастным слоем. Самостоятельно менять тему телефона или перезапускать его системные процессы приложение не пытается.

Наличие кнопочной панели определяется `WindowInsets.tappableElement` по нижнему и боковым insets. Для жестовой навигации сохранены прозрачность и цвет значков, соответствующий текущему экрану. Верхняя системная панель по-прежнему соответствует цвету занятия. Safe areas, часы, сигналы, данные и код Ads не менялись.

[Официальные правила Android 15 для кнопочной панели](https://developer.android.com/about/versions/15/behavior-changes-15): navigationBarColor продолжает действовать для трёх кнопок, а gesture navigation его игнорирует.

Проверка физического контраста на старом кадре отдельно дала 1.169:1 и правильно отклонила его. Нативная проверка 0.11.3 подтвердила улучшение физического контраста: светлая тема 6.561:1, тёмная 9.749:1. Старый кадр 1.169:1 проверка отвергает.
