# Прямой контроль SDK после исправления ID

11 ноября 2026. Цель: отделить ошибку production-конфигурации от красных demo-тестов. Исходник приложения закреплён на 8a74a4fe (код приложения совпадает с 2ac3ae5); SDK 8.6.0, Android 15 / API 35, эмулятор GitHub Actions с KVM. Физический телефон и боевые запросы не использовались.

## Условия

Отдельная ComponentActivity с обычным FrameLayout и прямыми BannerAdView / InterstitialAdLoader. Нет Compose, класса Ads, политики частоты и экранов приложения. BuildConfig ID и AppMetrica key пустые; тест использует только константы demo. SDK инициализируется явно, все SDK-вызовы идут с UI thread, loader/ad удерживаются до конца. Общие зависимости и Application проекта остаются; это контроль обёртки и интерфейса, а не отдельное чистое приложение без остальных SDK.

Два запуска с включёнными/выключенными системными анимациями. Фото и дерево каждого экрана, реальные callback events и scales сохранены в CI. Никаких кликов по объявлению/CTA, подмены impression или ручной отправки счётчиков. Тест нажимает только распознанные SDK close/skip либо обычную системную «Назад».

## Первый контроль

[Прогон 42992169169](https://github.com/DanilaH/tabata-bata/actions/runs/42992169169), код диагностического теста 607577533073f50f8c23e75fcae968d0cee89547. Jobs 130427435513 (animations on), 130427435754 (off). У обоих 3/5 PASS; две причины красного результата разобраны ниже.

| Сценарий | Анимации включены | Выключены |
| --- | --- | --- |
| demo-banner-yandex в InterstitialAdLoader | onAdLoaded, ожидавший отказ исследовательский assert FAIL | То же |
| Прямой demo-banner-yandex | loaded + impression PASS, нативный creative | То же |
| Прямой demo-banner-adfox-html | loaded + impression PASS | То же |
| Прямой demo-interstitial-yandex | loaded/shown/impression/closed PASS | То же |
| Прямой demo-interstitial-adfox-image | loaded/shown/impression; тест не нажал X, FAIL | То же |

У прямой Yandex-межстранички shown→closed 14,35 с (on) / 16,30 с (off). Это успешный callback SDK, не объявление закрытого экрана по timeout.

В проверке намеренно неправильного demo ID тестовый сервер вернул межстраничку за 3,24 / 3,01 с. Следовательно, этот эксперимент НЕ воспроизводит валидацию реальных R-M блоков и НЕ доказывает, что production-блок любого формата подходит межстраничке. Нельзя использовать исходный assert «обязательно должен быть load error» как критерий исправности SDK: это оказалась неверная гипотеза исследовательского теста.

У Adfox image на скриншоте явно виден крестик справа сверху. В accessibility tree у него нет id и contentDescription; исходный автомат его пропускал. Контрольная верхняя полоса содержит ровно два ImageView: меню слева и X справа. Этот конкретный timeout вызван распознаванием автотеста, а не доказанным отсутствием возможности закрыть объявление.

В другом, прежнем Yandex creative (actual UI, 42987998819/job 130413707004) ни крестика, ни metadata row на итоговом скриншоте нет; зато есть настоящий interstitial impression в логе. Обнаружение Adfox X не считается исправлением того отдельного случая.

Отключение анимаций не объяснило различия этого контроля: исходы одинаковы. Значения on: window/transition=1.0, animator_duration_scale отсутствует (системный default); off: все три=0.0.

## Уточнённый контроль

Диагностический тест c970147f29971d49ad484b092da905eaac03ea2f, [прогон 42993505092](https://github.com/DanilaH/tabata-bata/actions/runs/42993505092): animations on — 5/5 PASS (job 130431799274), off — 4/5 PASS (130431799766), Yandex video close timeout. Артефакты sdk-boundary-on 13842927164, sdk-boundary-off 13843875137.

Исследовательский mismatch-case записывает фактический load outcome без предположения об обязательном отказе. Для Adfox добавлено распознавание именно наблюдавшейся верхней SDK-полосы с меню и крестиком, не произвольного рекламного изображения. Yandex-баннер наблюдается ещё два штатных SDK refresh: один успешный нативный creative не должен скрывать возможный отказ последующего HTML. Дополнительных loadAd/синтетических impressions нет. Тесты приложения в main не ослабляются.

| Уточнённый сценарий | On | Off |
| --- | --- | --- |
| Неподходящий demo prefix — записать фактический исход | loaded, наблюдение сохранено | loaded, наблюдение сохранено |
| Yandex-баннер: initial + 2 штатных refresh | 3 loaded / 3 SDK impression / 1 loadAd | 3 / 3 / 1 |
| HTML Adfox-баннер | SDK impression PASS | PASS |
| Yandex-межстраничка | SDK shown/impression/closed PASS | shown/impression есть, closed нет за 90 с |
| Image Adfox-межстраничка | Нажат видимый X, SDK closed PASS | То же, PASS |

Yandex-баннер остался нативным на всех зафиксированных initial/refresh. Этот контроль не воспроизвёл проблемный direct-HTML вариант demo-banner-yandex и не доказывает исправление его отдельного отсутствующего impression.

Доказана ошибка распознавания Adfox X в автотесте: on input elapsed 242132 → SDK closed 242249 (117 мс), off 342295 → 342460 (165 мс). Исправленное распознавание перенесено в основной AdsDemoTest. В пользовательском приложении нет добавленной кнопки, принудительного закрытия или изменений рекламы; APK остаётся прежней.

При этом Yandex video close timeout воспроизведён в прямом SDK-контроле. Финальный экран и дерево совпадают по признакам с прежним actual UI failure: pageIndex=1, видео и CTA видны, SDK metadata/close отсутствуют, верхняя progress-полоса невидима. Лог off: loaded=229687, shown=229913, impression=231301; closed отсутствует. Следовательно, наш Compose/App/Ads не является необходимым условием этого сбоя. Это не доказательство конкретного дефекта внутри закрытого SDK: остаются SDK/creative/окружение и общие зависимости процесса. Контроль использовал обычные SDK skip/close и Android Back; точная роль последовательности этих действий отдельно не установлена.

Анимации нельзя объявить причиной: в первом off-прогоне тот же Yandex-сценарий закрылся. Второй on/off отличается исходом, но объявления/их состояние могли отличаться. Отключение анимаций не вводится в продукт как исправление. Принудительный overlay X, подмена callback и ослабление TLS не добавлялись.

## Что доказано о production

Предыдущие Secrets действительно совпадали; владелец исправил их, повторные проверки и configured-release PASS. В новой подписанной APK два разных R-M ID и нет demo ID. Это подтверждённое исправление конфигурации, но точная доля прежних 264 load errors из 278 request по этой причине ретроспективно не установлена: прежние события не содержали SDK error code.

После обновления сравнивать load errors, loaded, shown и impression раздельно, только для app_version=0.10.1; старые установки продолжают использовать прежние ID. Неполученный баннерный onImpression не равен ad_error и сам по себе не доказывает отсутствие начислений. Новая APK и SHA — в основном [рекламном отчёте](2026-11-11-banner-impressions.md).

Полный обычный CI a558cef после повтора compatibility API35 PASS; полный CI 8a74a4fe (42990187912) тоже PASS. Кандидат с исправленными реальными ID может быть установлен на телефон для нормальной проверки. Ни эти прогоны, ни диагностический mismatch не подтверждают все реальные load errors как следствие старых ID. SDK video close и direct-HTML callback остаются отмеченными ограничениями, готовность рекламы к публикации целиком не объявляется.
